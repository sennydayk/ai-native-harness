# design-options — 구조 결정

## 절차
1. PLAN.md(범위·제약)와 DOMAIN.md(데이터·사용 방식)를 읽는다. 코드는 쓰지 않는다.
2. 구조 2~3안을 표로 비교: 구성(스택·저장소·화면) / 장점 / 단점 / 구현 시간 / 이 요구에 맞는 정도.
3. **적정 설계 체크** — 각 안에 대해 답한다:
   - 이 요구에 DB·캐시·큐·인증·상태 관리가 정말 필요한가? (읽기 전용? 데이터 규모? 사용자 수?)
   - 남은 시간 안에 MVP를 끝까지 동작시킬 수 있는가?
   - 결과를 사람이 설명할 수 있을 만큼 단순한가?
   - 계산·판정 로직을 결정론적 코드로 분리했는가?
4. 추천안 하나와 이유를 제시하고 **사람의 선택을 기다린다**.
5. 선택 결과를 DECISIONS.md에 한 줄: 결정 — 근거 — 버린 대안과 이유.

## 규칙
- 기술 스택은 요구사항과 환경(이미 설치된 런타임)에 맞춘다. 기본값: 가장 빨리 띄울 수 있는 서버 하나 + 단순한 화면.
- 실무자에게 보이는 영향이 있는 결정이면 ask-draft(선택형)로 묻는다.

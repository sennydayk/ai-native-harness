# brief-breakdown — 과제 분해 (5분 안)

## 입력
- 과제 README와 안내 문서 (데이터 파일은 data-recon이 맡는다)

## 절차
1. `harness/templates/BRIEF.md`를 루트에 복사해 채운다.
2. **제출 요구사항**을 README 원문 표현 그대로 빠짐없이 체크리스트로 옮긴다. 파일명·경로·형식을 정확히.
3. 요청을 3줄로 요약한다: 누가 / 무엇이 불편한가 / 무엇을 원하는가.
4. **용어집**: README에 나온 업무·도메인 용어마다 일반적 의미를 적되, 이 과제에서의 의미는 비워 두고 상태를 "확인 필요"로 둔다. 추정을 사실처럼 쓰지 않는다.
5. **모호한 표현**: "빨리", "중요한", "이상한", "요령"처럼 기준이 없는 단어를 모은다. 각각이 인터뷰 질문이 된다.
6. **숨은 가정**: 사용자 수, 사용 시점·빈도, 데이터 형태·갱신 주기, 사용 환경, 권한 등 요청이 당연하게 전제하는 것.
7. **질문 후보** 8~12개: 인터뷰 사다리 단계(맥락 → 현재 방식 → 판단 기준·노하우 → 사례 → 사용자·성공 기준 → 제약 → 우선순위)별로, 각 질문이 **어떤 설계 결정에 영향을 주는지**와 우선순위를 붙인다.
8. **묻지 말 것**: 해결책을 요구하는 질문("무엇을 만들면 되나요", "할 일을 알려주세요")은 업무 방식을 묻는 질문으로 바꿔 적는다.

## 규칙
- 해결책을 미리 정하지 않는다. 이 단계의 산출물은 질문이다.
- 질문 후보는 실무자에게 한 번에 1~2개씩 보낸다 (목록 통째 전송 금지).
- 확인된 용어는 domain-notes로 DOMAIN.md에 옮기고 BRIEF의 상태를 "확인됨"으로 바꾼다.
